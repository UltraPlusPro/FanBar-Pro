顺带修掉的既有缺陷（真实崩溃级）
--------------------------------

    "%.0f°C · %.0f%%"  →  "%,0f°C · %,0f%%"    （葡萄牙语、乌克兰语）

不存在的参数。这些 catalog 此前**没有测试文件**，所以一直没被发现。本版：

三条边界（都已用单测钉住）
--------------------------
0. **tooltip 不再把「显示的数值」标成「控制输入」**（QA 回归 DEF-3）。
   同一份采样下 显示 78°C / 控制 61°C 时，旧 tooltip 输出
   「控制输入：CPU 最热核 · CPU 平均 61°C · 最高 78°C」——数值都对，
   但把最热核说成了控制输入。现按口径分别表述：
     · 选最热核：「显示：CPU 最热核 78°C · 控制输入：CPU 平均 61°C」
     · 选平均  ：「显示：CPU 平均 61°C · 风扇控制使用同一数值（最高 78°C）」
     · 曲线会话：「显示即控制输入：CPU 平均 55°C」（两者本就是同一个数，
       不再用两个标签重复同一数值）
   同时 `MenuBarDisplayMode` 的 title/detail 改为按口径动态生成，
   例如选最热核时「显示内容」不再写「显示温控曲线的输入温度」。
   单测：testHottestCoreTooltipDistinguishesShownValueFromControlInput、
   testSoCAverageTooltipSaysShownValueIsTheControlInput、
   testDisplayContentCopyFollowsTheTemperatureLogic。

1. **只影响菜单栏显示。** 风扇控制输入仍是 SoC 平均：
   `displayTemperatureCelsius` 与 `temperatureHistory[].cpuCelsius` 未改。
   MenuBarTemperatureSourceTests 直接断言同一份采样下：
       menuBar(.socAverage) = 61、menuBar(.hottestCore) = 78、
       displayTemperatureCelsius = 61（控制输入不动）
2. **默认值与 1.1.6 一致。** 未设置/未知值时回落到 .socAverage，
   所以老用户升级后读数完全不变。
3. **曲线态优先曲线输入。** 曲线会话进行中，两种口径都显示曲线自己的
   输入温度（就是用户正在据此调节的那个数），不显示最热核。

为什么用方案 A（app 内窗口）而不是方案 B（独立可执行）
----------------------------------------------------
TipDemo 依赖 SwiftUI + AppKit 与 `Bundle.main` 里的 PNG，做成独立可执行需要
再写一套签名与路径解析。app 内窗口让界面、图片、源码全部落在同一个
`codesign` 封条内，`codesign --verify --strict` 天然覆盖，且离线可用
（不需要网络即可显示界面与二维码）。

页脚为什么不加第三个链接
------------------------
试过把「在浏览器中打赏」放进页脚，被既有测试
`SettingsSupportFooterTests.testFooterFitsOneLineInEveryLanguage` 拦下：
乌克兰语单行宽度 520pt > 可用 512pt。因此浏览器入口改放打赏窗口内部，
页脚保持「免费开源 · 支持开发」两项，所有 11 种语言都能单行放下。

四、放弃 ADHoc 签名（全包 Local QA）+ 源码继续内嵌 + 充分冒烟
================================================================

scripts/package-app.sh
----------------------
· **ad-hoc 变成硬失败**：FANBAR_SIGN_IDENTITY 为空或为 `-` 时直接 exit 2，
  不再有 ad-hoc 兜底分支。
· 签名前先 `security find-identity -v -p codesigning` 校验该身份真实存在，
  打错字不会悄悄降级成别的签名者。

调用方同步（QA 回归：只改脚本不调用方，CI 必红）
------------------------------------------------
· .github/workflows/macos-release.yml 的 build job 原来用
  `FANBAR_SIGN_IDENTITY: "-"` + `FANBAR_ALLOW_ADHOC: "1"` 去跑 package-app.sh，
  在 ad-hoc 变成硬失败后必然 exit 2。现改为从 `secrets.FANBAR_SIGN_IDENTITY`
  读取真实身份，并新增一步「Require a signing identity」：缺失或为 `-` 时
  直接失败并打印清晰的配置提示（不再静默 ad-hoc）。
· 同一 job 的 verify 步骤写死 `dist/FanBar.app` / `Contents/MacOS/FanBar`，
  与真实产物 `dist/FanBar Pro.app` / `Contents/MacOS/FanBar Pro` 不符，
  已全部改正（release job 的同类路径一并修正）。
· scripts/build-dmg.sh 默认输入 `dist/FanBar.app` → `dist/FanBar Pro.app`。
· scripts/test-dmg.sh、scripts/release-local.sh 的同类路径一并修正。
· 6 份 README（en / zh-CN / zh-TW / ja / fr / ru）、CONTRIBUTING.md、
  README-构建说明.txt 里教用户跑
  `FANBAR_ALLOW_ADHOC=1 FANBAR_SIGN_IDENTITY=-` 的段落，全部改为
  「必须提供真实签名身份，本地自签用 `Local QA Code Signing` 之类真实身份名」，
  并明确写出「ad-hoc 已不再支持，会直接失败」。
· 源码说明-1.1.5.txt 标注为历史文档（其 ad-hoc 做法已过时）。
· 注意：DMG **内部**仍命名为 `FanBar.app`，这是 Homebrew cask 的安装约定
  （Casks/fanbar.rb 的 `app "FanBar.app"`），不是构建产物路径，保持不变。
· 内嵌源码 zip 仍在 codesign **之前**放入 Contents/Resources/Source/，
  因此被 `_CodeSignature/CodeResources` 密封。
· 新增打赏资源的存在性断言（TipWechat.png / TipAlipay.png 非空），
  缺图会让窗口空白，比构建失败更糟。

必须区分的三种情形
------------------
· 用户主动交还 macOS / 停用控制服务 → **不弹**（helperState 已不是 .enabled，
  且 quit 时已关闭上报）
· 曲线会话进行中掉线 → **弹**
· 已加载但进程消失 → **弹**（由 launchd 状态变化触发）
· 同一次掉线 10 分钟内只弹一次；启动后 20 秒内不弹（正常启动会重新注册 helper，
  那一下不能算故障）

六、高温提醒「提醒温度」右侧数值改红色
================================================================

· Sources/FanBar/FanBarSettingsView.swift thresholdRow：
    PanelPalette(colorScheme:).warmInk  →  Color(nsColor: .systemRed)
  理由：这个数字本身就是告警阈值，红色让它读作「上限」而不是又一个可调数值；
  同时 `.systemRed` 会跟随「增强对比度」与浅/深色外观。
· 面板与曲线上的告警线**不改**（仍用 palette 的 warm/hot 分级）：那里是
  数据可视化，颜色语义是「温度高低」，改成纯红会与 hot 级别撞色，
  反而削弱分级。设置页里是一行文字，用它承载「这是告警」最有效。
